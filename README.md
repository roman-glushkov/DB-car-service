# AutoPro — три кабинета на одной MariaDB

Обновление расширяет существующий проект на Node.js + Express + MariaDB. Переход на SQLite не выполняется. Старые таблицы и записи клиентов, автомобилей, заказов, сотрудников, работ, запчастей и оплат не удаляются.

## Что добавлено

- Отдельные точки входа: `/admin/login`, `/client/login`, `/employee/login`.
- Отдельные интерфейсы: `/admin`, `/client`, `/employee`.
- Авторизация по email и паролю. Пароли сохраняются как хеши scrypt, cookie сессии имеет HttpOnly и SameSite=Strict.
- Три защищённых API-пространства: `/api/admin/*`, `/api/client/*`, `/api/employee/*`.
- Администратор видит старую административную панель и страницу «Доступы пользователей».
- Клиент видит только автомобили, заявки и историю, связанные с его `client_id`; может добавить автомобиль, загрузить фото и создать заявку.
- Сотрудник видит только заказы, назначенные ему через `orders.employee_id` или `order_works.employee_id`; может обновить разрешённый статус, диагностику и комментарий.
- При создании заявки клиентом сервер подбирает активного сотрудника по навыкам и текущей загрузке.
- При переназначении заказа администратором обновляется исполнитель и в строках `order_works`.
- Фотографии автомобилей хранятся в `uploads/cars` (до 5 МБ, JPG/PNG/WebP).

## Важно перед запуском

1. Сделайте резервную копию вашей текущей базы `autoservice`.
2. Сохраните свой действующий `.env`. Не заменяйте его файлом `.env.example`, иначе можно потерять настройки подключения к вашей MariaDB.
3. В архиве `database/schema-dump.sql` — исходный снимок начальной схемы на 10 таблиц. Ваш действующий сервер уже расширен до 12 таблиц миграцией `002_skills_and_order_events.sql`. Этот дамп не является актуальным полным дампом рабочей базы.

## Настройка существующей MariaDB

Поскольку в вашей базе уже есть 12 таблиц, **не запускайте повторно миграцию 002 без необходимости**. Для этого обновления требуется только новая таблица аккаунтов:

```sql
USE autoservice;
SOURCE database/migrations/003_user_accounts.sql;
```

Либо выполните файл `database/migrations/003_user_accounts.sql` через MySQL Workbench / HeidiSQL.

Миграция создаёт только `user_accounts`. Она не удаляет, не очищает и не пересоздаёт старые таблицы. После неё в базе будет 13 таблиц.

Если разворачивать базу с нуля из исходного 10-табличного снимка, порядок такой:

1. Импортировать `database/schema-dump.sql`.
2. Выполнить `database/migrations/002_skills_and_order_events.sql`.
3. Выполнить `database/migrations/003_user_accounts.sql`.

## Настройка `.env`

Оставьте действующие `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` и `PORT`. Добавьте в существующий `.env` строку:

```env
SESSION_SECRET=ВСТАВЬТЕ_СЮДА_СЛУЧАЙНУЮ_ДЛИННУЮ_СТРОКУ
```

Сгенерировать значение можно командой:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

Не публикуйте `.env`, пароль MariaDB или пароли аккаунтов. Для размещения в интернете используйте HTTPS и `NODE_ENV=production`; при production-cookie флаг Secure включается автоматически.

## Установка и запуск

В терминале из папки проекта:

```bash
npm install
npm start
```

Откройте `http://localhost:3000/login`.

## Создание первого администратора

После применения миграции создайте хотя бы одну административную учётную запись. Используйте реальный надёжный пароль:

```bash
node scripts/create-account.js admin admin@autopro.local "ChangeThisPassword123!"
```

Это команда создания аккаунта, а не регистрации через сайт. Первый администратор нужен для входа в админку.

После входа в админку откройте **«Доступы пользователей» → «Создать доступ»**. Там можно привязать существующего клиента или сотрудника к отдельному логину и паролю. Для клиента выбирается запись из `clients`, для сотрудника — запись из `employees`.

## Первый сценарий проверки

1. Войдите администратором через `/admin/login`.
2. В «Сотрудниках» откройте мастера и назначьте ему навыки, совпадающие с видами работ из `work_types`.
3. В «Доступах пользователей» создайте вход для существующего клиента и для этого мастера.
4. Откройте `/client/login`, войдите клиентом. Добавьте автомобиль, при необходимости загрузите его фото, затем создайте заявку и выберите виды работ.
5. Администратор увидит новый заказ в старой административной панели и сможет проверить автоматическое назначение.
6. Войдите сотрудником через `/employee/login`: заказ будет отображаться в «Моём дне» / активных работах. Мастер сможет сохранить диагностику, комментарий и разрешённый статус.
7. Вернитесь в клиентский кабинет: статус и история заказа будут доступны клиенту.

Если у сотрудника не настроены навыки для всех выбранных работ, автоматическое назначение может оставить заказ без мастера. Тогда администратор должен назначить подходящего сотрудника вручную.

## API и права

- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me` — вход, выход и проверка сессии.
- `/api/admin/*` — административные маршруты прежней панели. Они требуют роль `admin`.
- `/api/client/*` — клиентский профиль, его автомобили, заявки и история. Все запросы ограничены `client_id` сессии.
- `/api/employee/*` — рабочие заказы и обновления сотрудника. Сервер проверяет назначение на конкретный заказ.

Старые административные URL API также оставлены для совместимости, но закрыты серверной проверкой роли администратора. Клиент и сотрудник не получают к ним доступ.

## Фото и резервные копии

Фотографии загружаются в `uploads/cars`. Добавьте эту папку в резервное копирование вместе с MariaDB, если фото важны.

После применения миграции `003` обновите структурный дамп из вашей **реальной текущей базы**:

```bash
mysqldump -u root -p --no-data autoservice > database/schema-dump.sql
```

Для полной резервной копии с данными используйте отдельный файл и храните его безопасно:

```bash
mysqldump -u root -p --single-transaction autoservice > autoservice-backup.sql
```

Не импортируйте резервную копию обратно в уже работающую базу только ради обновления файла дампа.

## Ограничения текущей версии

- Первый администратор создаётся через CLI; следующие аккаунты можно создавать из админки.
- Сброс пароля по email, SMS-коды и двухфакторная аутентификация пока не реализованы.
- Фото хранятся локально на сервере приложения; для нескольких серверов понадобится общее объектное хранилище.
- Проверка синтаксиса JavaScript выполнена. Для полного функционального теста нужно запустить архив на вашей машине с доступом к вашей MariaDB и проверить сценарий по разделу выше.
